# 첫 접수 흐름에서 드러난 재시도 구간

도메인·검증·HTTP 클라이언트·아웃박스를 붙인 첫
`src/main/java/com/sportsbook/betting/placement/BetPlacementService.java`는 이해하기
쉬운 직선 흐름이었다.

```text
DB 멱등 재생
  → 슬립·가격 검증
  → PENDING 저장
  → 위험 한도 확인
  → 지갑 차감
  → ACCEPTED + 아웃박스
```

## 준비한 아웃박스를 수락 트랜잭션에 붙였다

앞선 커밋에는 아웃박스 테이블과 사건 팩터리만 있었다. 첫 접수 구현에서
`BetPlacementService`가 지갑 응답까지 받은 PENDING bet으로 페이로드를 만들고,
[`BetStore.acceptAndEnqueue()`](../src/main/java/com/sportsbook/betting/placement/BetStore.java)가
상태 전이와 행 저장을 한 트랜잭션에 묶었다.

```java
bet.accept(now);
outbox.save(event);
return bet;
```

직렬화는 이 트랜잭션에 들어가기 전에 끝난다. 직렬화가 실패하면 bet은 PENDING에
남고, 트랜잭션이 시작된 뒤에는 `ACCEPTED`와 이미 고정한 페이로드가 함께 커밋되거나
함께 롤백된다. 발행기가 나중에 베팅 집계를 다시 읽어 다른 사건을 만들지
않는 경계도 이때 완성됐다.

Redis의 `SETNX`로 처리 중인 멱등 키를 예약하고 PostgreSQL 유일성 제약을 최종
보장으로 썼다. 위험 관리나 지갑 서비스의 `BetPlacementException`이 오면 PENDING을
`REJECTED`로 바꿨다. 모든 의존 서비스 실패가 “상대가 아무 일도 하지 않았다”는
전제에서는 동작하지만 네트워크에는 그 전제가 없다.

지갑 서비스가 차감하고 응답만 유실하면 로컬은 거절되거나 PENDING으로 남을 수 있다.
위험 한도 확인은 예약이 아니어서 확인과 차감 사이에 한도가 바뀔 수 있다. Redis
예약을 본 동시 요청은 첫 DB 행이 아직 보이지 않을 때 바로 409를 받기도 한다. 같은
본문의 동시 요청이 하나의 저장 결과로 수렴하지 못하는 구간이다.

## 수락 뒤 아웃박스 행을 보내기 시작했다

첫 접수 흐름 뒤 `OutboxPublisher.publishPending()`이 추가됐다. 1초마다 생성 시각이
앞선 미발행 행을 최대 100개 읽고, 각 브로커 확인을 최대 5초 기다린다. 성공한
엔티티에 `published_at`을 표시하고 실패한 행은 다음 실행에 남긴다.

```java
for (OutboxEvent event : batch) {
  if (sendBlocking(event)) {
    event.markPublished(clock.instant());
  }
}
```

확인 뒤 `published_at` 트랜잭션이 커밋되기 전에 프로세스가 종료되면 같은 행이
재발행된다. 발행자의 `enable.idempotence=true`는 한 발행 세션 안의 브로커 재시도를
도울 뿐 애플리케이션 재시작과 DB 롤백을 묶지 않는다. 전달은 최소 한 번 방식이며
소비자가 사건 ID나 도메인 키로 중복을 흡수해야 한다.

생성 시각 순 조회도 엄격한 발행 순서는 아니다. 한 행이 실패해도 반복문은 다음 행을
계속 보내므로 같은 사용자 키의 뒤 사건이 먼저 도착할 수 있다. 조회할 때 행을
점유하지 않아 여러 발행기 인스턴스가 같은 묶음을 고를 수도 있다. 사용자 ID 파티션
키는 전송된 레코드를 같은 파티션에 모으지만 이 두 빈틈을 닫지는 않는다.

발행기는 `@Transactional` 메서드 안에서 최대 100번의 확인을 순차 대기한다.
브로커가 느리면 DB 연결과 트랜잭션도 오래 열린다. 병렬화나 행 점유를 추가하려면
같은 파티션의 업무 순서, 여러 발행기의 중복 선택과
`published_at` 갱신 방식을 함께 바꿔야 한다. 발행된 행은 삭제하지 않아 운영
재발행 근거가 남지만 보존 기간과 정리 작업은 구현돼 있지 않다.

## 첫 복구 작업도 행동을 조회처럼 사용했다

초기 `BetReconciliationJob`은 오래된 PENDING을 읽어 지갑 차감 요청을 다시 보냈다.
bet ID가 지갑 서비스의 멱등 키라 두 번 차감되지는 않는다는 생각이었다. 성공하면
bet을 수락하고 잔액 부족이면 거절했다.

이 방식은 “같은 명령 재시도”로 차감 여부를 알아낸다. 지갑 서비스가 키를 오래
보존한다는 전제에는 맞지만 위험 한도 상태와 어떤 외부 단계까지 끝났는지 로컬에
기록하지 않는다. 프로세스가 위험 한도 확인 뒤, 지갑 차감 뒤, 수락 직전에 죽은
경우가 모두 같은 PENDING으로 보인다. 의존 서비스의 404와 시간 초과도 별도 증거
조회 없이는 구분할 수 없다.

## 한 개 상태로는 다음 행동을 정할 수 없다

복구 가능한 작업 흐름이 답해야 할 질문은 단순히 “PENDING인가”가 아니다.

- 위험 한도가 예약됐는가, 이미 확정됐는가, 만료됐는가
- 지갑 차감이 적용됐는가, 그 작업 ID는 무엇인가
- 정방향 진행 중인가, 위험 한도 해제나 지갑 환불로 방향을 바꿨는가
- 같은 멱등 키의 최초 판정이 성공 bet인가, bet을 만들기 전 거절인가

초기 모델에는 이 증거가 없어 장애 뒤 행동을 추론했다. 추론이 틀리면 차감 뒤 거절,
위험 한도 없는 수락, 보상 뒤 재수락 같은 문제가 생긴다.

그 결과 위험 관리 API는 단순 확인에서 bet ID를 따르는 예약 생명주기로 바뀌었고,
지갑 서비스에는 차감 조회가 필요해졌다. bet에는 접수 단계와 외부 작업의 증거가,
`placement_request`에는 멱등 키·요청 지문·확정 결과가 추가됐다. 외부 호출도 긴
DB 트랜잭션에서 떼어내 단계별 짧은 트랜잭션 사이에 놓였다.

첫 구현의 아웃박스는 수락 이후의 유실만 막았고, 수락 전에 HTTP 호출로 생긴 외부
효과는 복구하지 못했다. 현재 상태 머신은 그 앞쪽 공백을 채웠으며, 뒤 기록의 각
진행 지점은 여기서 답하지 못했던 질문에 대응한다.
