# 베팅 접수 부하 테스트 결과

2026년 5월 29일 macOS Apple Silicon과 Docker Desktop 환경에서 측정했습니다.
PostgreSQL, Redis, Kafka, WireMock, betting JVM이 같은 Docker VM의 자원을
공유했고 k6는 호스트에서 실행했습니다. 실제 risk와 wallet 대신 항상 승인하는
WireMock을 사용했습니다.

## 지속 접수

각 요청은 슬립 검증, Redis 배당 확인, risk와 wallet HTTP 호출, 상태 저장, outbox
기록까지 전체 접수 과정을 수행합니다.

| 목표 RPS | 실측 RPS | 오류율 | p50 | p95 | p99 |
|---:|---:|---:|---:|---:|---:|
| 150 | 149.6 | 0% | 91.5ms | 120.7ms | 148.5ms |

오류율 목표 0.1% 미만은 만족했지만 p95 50ms 미만과 p99 100ms 미만은 만족하지
못했습니다. 하나의 VM에서 두 번의 HTTP 왕복, 두 번의 데이터베이스 트랜잭션,
Redis 조회와 Avro 직렬화를 함께 처리한 결과입니다. 이 측정만으로 호스트 자원과
구조적 한계 중 어느 쪽이 원인인지 단정할 수는 없습니다.

원본 결과: `2026-05-29/placement_load_150.json`

## 순차 멱등성

하나의 VU가 같은 `Idempotency-Key`로 요청을 50회 보냈습니다. 모든 응답은
HTTP 201이었으며 첫 응답과 같은 `betId`를 반환했습니다.

원본 결과: `2026-05-29/idempotency.json`

## 동일 키 동시 요청

100개 VU가 같은 키로 한 번씩 요청했습니다. 모든 응답은 201 또는 409였고 5xx는
없었습니다. 다만 이 스크립트는 수락된 식별자, 데이터베이스 행, wallet 차감 횟수를
수집하지 않습니다. 따라서 단일 수락과 단일 차감은 이 결과로 증명되지 않습니다.

원본 결과: `2026-05-29/concurrency.json`

## 해석할 때 주의할 점

Apache HttpClient의 기본 커넥션 풀도 시험했지만 route당 기본 5개 연결이 병목이 되어
p99가 수 초까지 늘어났습니다. 현재 환경에서는 JDK HttpClient가 더 나았으며, 실제
운영에서 Apache HttpClient를 사용하려면 트래픽에 맞춘 풀 크기 조정이 필요합니다.

새 결과는 `results/<YYYY-MM-DD>/`에 저장합니다. 개발 환경과 운영에 가까운 분산
환경의 결과는 같은 값으로 비교하지 않고 별도로 기록합니다.
